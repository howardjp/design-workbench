# Origin-site fidelity audit: Martlet and Krigsvold

October 23, 2026 · Audit of implementation `594055a647a84fa30bb400c98810f946b66a7c0b`

**Finding: the implementations are useful experiments, but neither language's grammar is locked. Origin fidelity has not been established.** Earlier descriptions of the reference applications as using the original palettes and native compositions were too broad. Correct fonts, original theme-site SVGs, working interactions, and passing tests do not establish fidelity of the rendered objects.

This is the requested inventory and disposition pass. It records what differs first, then recommends what should differ. It does not silently turn those recommendations into a replacement design. The deployed references remain the audited implementation so that the differences can be reviewed against a fixed baseline. No origin site, package implementation, Site deployment, or distributed builder skill was changed by this audit.

## Authority and evidence

1. The actual object on the originating website is the default authority for its existing use and context.
2. Source markup, styles, scripts, and computed browser styles explain that object. A token's presence in a package does not prove that the origin uses it for that purpose.
3. The adopted charters describe direction and a feedback process. They do not ratify every later implementation choice.
4. A genuinely new application need can justify an extension. Its anatomy, values, states, accessibility, responsive behavior, rationale, and relationship to existing objects must be stated. Until evaluated, it is a proposal.
5. A departure from a working origin object requires a demonstrated problem and a tested replacement. Personal preference, symmetrical differences between families, and template convention are insufficient.

## Difference register and recommended dispositions

**Restore** means use the demonstrated source object for the comparable context. **Remove** means the addition lacks a demonstrated job or conflicts with that object. **Extension** means the capability has a real application purpose, but its new visual/interaction rules need an explicit specification. **Host** means application content or identity may differ; it is not a universal language rule. **Unresolved** means evidence does not establish a choice. These are review outcomes, not claims that remediation has shipped.

## What should legitimately differ

- **Consumer identity and content:** design-system names/marks, documentation destinations, examples, API tables, download links and application data. A language must work with the consumer's own identity.
- **Task framing:** article, bounded form, comparison workspace and focused editing can choose different compositions in either family. Source site navigation counts and photographic heroes are not mandatory for every app.
- **New capabilities:** native selection controls, editor validation, saving, recovery, data paging, tabs and switches need explicit extensions where origins do not exercise them. Preserve safe, accessible behavior while reviewing its form.
- **Available-space adaptation:** a nested panel cannot blindly use a page-wide viewport breakpoint. A justified container-based translation may differ while preserving the source relationship and reading order.
- **Accessibility fixes:** demonstrated defects should be corrected and fed back to the origin, with evidence. Origin authority is not a reason to retain an inaccessible interaction.

What should not differ without such a reason: an existing popup's surface, its pointer/shadow/radius, TOC hierarchy, prose/link/heading roles, control geometry, contextual accent placement, and the meaning of borders and grouping.

## Remediation order and grammar acceptance

1. **Reconcile the existing objects.** Remove N01/N10, replace N04–N08 with source-context navigation, and restore R01–R07. Address the foundation-versus-semantic role mismatch before comparing layouts by eye.
2. **Restore smaller lost distinctions.** Buttons/fields, table headers/density, quotes, code, type/label roles and source variants. Remove decorative mono, arbitrary stripes, and family-exclusive arrangements.
3. **Specify the true extensions.** For each new object: job, source ingredients, anatomy, dimensions/tokens, states, interaction, content, responsive behavior, acceptance evidence, counterexample, and maturity. Unsupported decoration is deleted; useful new functionality is specified.
4. **Build matched source specimens.** Same content/state/width as the source object, with paired captures and computed styles. Include desktop and mobile submenu contexts, both Martlet TOC variants, nested widths, focus, long labels, and enlarged text. Acceptance requires explaining every remaining meaningful difference.
5. **Ratify the grammar from this record.** A grammar rule needs an observed source relationship or a justified evaluated extension, applicable contexts, explicit exceptions and evidence. Update components, docs, MCP references and builder skills together only after the decision is concrete; regenerate distributions with provenance.
6. **Then broaden the application trials.** Run the form/table/dashboard/collection comparisons against the reconciled rules. The notebook's success is evidence of a promising experiment, not ratification of the language.

## Inventory, reproducibility, and limits

The companion `origin-audit-2026-10-23/` directory contains a source manifest, an exhaustive declaration inventory for the seven authored stylesheets and both actively imported theme/foundation pairs, a 44-export component inventory, an inline-style accounting, and totals. There are **613 style rules and 2,114 declarations**: 1,600 authored declarations and 514 imported theme/foundation declarations. Four inline style/mode assignments are separately accounted for. Every declaration carries an audit category and register IDs. Exact property/value matches are search leads, not proof of equivalent context or visual fidelity. A rule can combine source-derived typography with untraced spacing; its shared audit category does not certify all its declarations.

The generation script takes a local cache of the pinned origin files. That cache was populated through authenticated GitHub file reads, including all files in the scoped component/layout/style directories, and is not copied wholesale into this repository. All **49 source files** were verified against their original Git blob identities. The manifest preserves repository, commit, original blob identity, local content hash and source URL for independent retrieval. The generator can be rerun after retrieving the same files into the documented cache layout. Source declarations include inherited framework CSS as search evidence; unused framework selectors do not establish actual origin use.

Typography/font loading, original SVG identity and build selection were also inspected. The declaration CSV inventories authored UI CSS and active theme/foundation values; it does not expand every font-file unicode-range rule. Site-specific seasonal treatments, the Ukraine banner, analytics/consent policy and personal/institutional imagery remain host concerns. Their presence at an origin does not require every adopting application to reproduce them. Inspect real code/media/source fixtures when closing the corresponding outstanding findings.

This pass is a comprehensive **source-level design accounting**, with direct live checks of the reported source header, dropdown, document index and prose. It is not a new pixel comparison of every deployed route/state or an accessibility certification. Undemonstrated framework defaults, optional token roles and new application objects remain explicitly unproven. Previous CI verifies the implemented behavior; it does not decide whether that behavior or styling is the right grammar. No broader application stress test is accepted as a substitute for closing these origin-fidelity findings.
